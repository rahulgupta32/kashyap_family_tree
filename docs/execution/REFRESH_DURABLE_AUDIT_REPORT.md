# Durable refresh rotation evidence — 2026-10-10

Refresh processing now records an UPDATE audit intent in the same row-locked PostgreSQL transaction as successor creation, replay-driven account-session revocation or expiry-driven session revocation. The payload contains only a fixed outcome and, for rotation, the successor session ID. Existing actor/session/IP/user-agent governance remains; no refresh token or token hash is placed in the payload. REFRESH_ROTATED describes a committed session mutation, not a guarantee that credentials reached the client or that the later account checks passed.

Audit insertion failure during normal rotation rolls back successor creation and old-session revocation. An unconfirmed commit returns bilingual 503 with no replacement credentials; it does not delete potentially committed evidence, reissue credentials or automatically retry rotation. A client whose successful rotation acknowledgement was lost may need a fresh OTP. Immediate audit-delivery failure retains the committed event with bounded retry scheduling and a fixed error code; raw database/delivery diagnostics are not logged by this path.

Replay response must not depend on healthy audit insertion. If a replay was observed but the combined transaction acknowledgement fails, the service separately attempts account-wide revocation and returns 503 without credentials. Fixed incident codes distinguish unconfirmed audit evidence and unconfirmed fallback revocation. This fallback deliberately preserves the prior security response rather than promising cross-transaction atomicity: an evidence outage can leave revocation without the replay audit event. A complete database outage can prevent confirmed revocation. Production incident alerting/reconciliation remains required.

Unknown tokens cause no session mutation and do not allocate a durable event per request. Admission protection/telemetry for refresh, DTO/guard rejection evidence, post-rotation account/privileged rejection evidence, all other revocation paths and signed retention/incident acceptance remain open. The repository callback is optional for direct low-level callers; the production AuthService requires durable evidence dependencies and supplies the callback for every refresh operation. No migration or public response contract change is required.

Verification: local API TypeScript checking and 311 unit tests passed at the initial implementation checkpoint. Eight dedicated real-PostgreSQL regressions cover redacted committed successor linkage, insert-failure rollback, lost commit acknowledgement, retryable delivery failure, replay revocation, expiry, replay evidence outage fallback and concurrent refreshes. These integration cases require execution in CI; collection is not acceptance. Exact commit/run outcomes are recorded in PR #5 after publication.
