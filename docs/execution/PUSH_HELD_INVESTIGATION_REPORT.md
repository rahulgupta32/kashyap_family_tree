## Implemented behavior

`GET /audit/delivery/pushes` lists open PUSH dispatches requiring investigation: failed/held parents, retained unknown/rejected device attempts and expired provider claims. Ordinary pending dispatches, completed history and other channels are excluded. Results are oldest first with a default page of 20, maximum 50, and an opaque timestamp/UUID keyset cursor. PostgreSQL microseconds are retained to avoid skipping records with sub-millisecond timestamps or tied creation times. Invalid query keys, dates, identifiers, cursors and limits are rejected.

`GET /audit/delivery/pushes/:id` inspects a retained PUSH parent, including one that has since resolved. Parent and device outcomes use one SQL statement snapshot. At most 50 device attempts are returned; an oversized roster fails unavailable rather than showing partial evidence. Each attempt distinguishes the immutable state, matching-claim provider observation, interpreted effective outcome and expired-claim flag. A late observation can interpret UNKNOWN consistently with the existing reconciler. An expired SENDING attempt remains SENDING, with its expiry visible. Missing evidence does not imply acceptance. Provider acceptance never proves delivery to a device.

Both routes require an authenticated current Super Admin, an active account, a live non-owner-revoked session with authentication under one hour old, and verification matching the currently enabled authenticator generation in every environment. Authority and factor checks run in the same database transaction under existing account/session/role/factor locks. The shared check also preserves the existing two-person audit recovery policy and rejects owner-revoked sessions there. Responses are no-store and project only dispatch IDs/status/time and attempt IDs/state/outcomes/flags. Recipient identity, token/registration/generation/claim IDs, receipts/hashes, event type, payload and raw provider/database errors are omitted. Dependency failures have a fixed unavailable response.

The bilingual audit console adds labelled keyboard-operable refresh, inspection and next-page controls and an authenticator link. Successful responses are validated and explicitly projected before rendering. Failed or malformed responses clear old data; role, identity, token changes and unmount abort pending requests. An empty roster explicitly infers no provider result. There is no resend/retry action and the service has no provider dependency or notification/evidence write. Pagination is a live operational view: concurrent reconciliation may remove records between pages; refresh starts at the oldest current records.
