# Community report evidence and central escalation checkpoint

Migration 034 gives reports exact bigint evidence cursors and a nullable reported post version. Existing report versions remain unknown rather than reconstructed. New reports retain the original reason/version; a duplicate open report does not overwrite evidence or increment the post again when the actor still has access. The existing current membership, branch and pending-post visibility checks still apply before duplicate detection.

An independent currently scoped moderator can browse report reasons, status, reported version, review notes and timestamps. Authors (including moderator authors), ordinary readers and foreign branch moderators cannot browse report cases. Responses omit reporter, submitting moderator and resolving moderator identities. Reports and escalations paginate separately in pages of at most 50, using validated bigint strings without JavaScript precision loss. Sequence ordering is ingestion order; pre-migration reports do not acquire invented historical chronology. Revision and moderation history remain separate authorized sources for content/decision context. Deleted posts return 404 while database evidence is retained.

An independent scoped moderator can escalate a current PENDING post with a reason and viewed version. Post locking, a unique open-case index, version increment and transactional audit intent prevent duplicate/stale escalation. The post remains hidden from ordinary readers. While an escalation is OPEN, publication/rejection requires an independent CENTRAL_ADMIN or SUPER_ADMIN; author exclusion and the existing different-original-reviewer rule for appeals continue to apply. The central queue already includes scoped pending posts. Content, image and sharing edits do not remove the open escalation. Central moderation resolves escalations/reports and records the existing durable decision atomically; existing generic outcome notices apply. Author/scoped moderator deletion retains existing authority and withdraws the open escalation. Escalation is an audit-only action; no new external escalation messages are sent.

Web and Flutter provide private evidence history with older/latest navigation, explicit central escalation and waiting status. Branch review buttons disappear while escalation is open; server authorization remains authoritative. The native escalation form carries the viewed version and reason. This establishes a bounded manual central-review workflow, not an approved configurable risk/category policy, automated triage, staffing/service-level obligation or emergency response mechanism.

Three added real PostgreSQL HTTP cases cover privacy/scope, central resolution across author edits, competing escalation, stale/forged requests, audit rollback, deletion/retained withdrawal and independent bounded report/escalation pagination. One unit case validates cursors/identity/version integrity before persistence. The live browser scenario reads a report and records/reads escalation; one mocked native HTTP/widget case verifies private evidence and viewed-version escalation. Dedicated case-workflow device/provider/load/security acceptance is not claimed.

Local typechecks, API/admin production builds, the existing 165-test unit run plus the updated seven-test community suite, 31-scenario browser collection, frozen assessment validation and diff checks passed.
