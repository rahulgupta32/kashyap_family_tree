# Idle database connection recovery

Push CI 38154464739 at `5a4e44b18b36e46097bcb221dcfe110333cbe6fd` passed 359 unit and all 478 integration assertions, but its calendar-delivery suite failed on an unhandled idle PostgreSQL error (`57P01`) when an administrator terminated a connection. That run remains FAILED. Inspection found neither main nor media-journal pg-pool registered its mandatory idle-client error listener. Such errors occur outside query promises and can terminate the process; the integration teardown exposed a production resilience gap rather than a reason to ignore a failed suite.

Both real pools now retain error listeners that emit fixed pool classifications and allowlisted SQLSTATE only. Main idle errors clear readiness. A successful explicit database health probe restores readiness; a failed probe clears it. pg-pool discards failed idle clients and may create replacements on subsequent queries; this change does not replay an interrupted transaction or claim that an unconfirmed commit rolled back. Journal failures retain independent diagnostics and the existing durable media-write protocol.

Two new real PostgreSQL cases acquire actual main/journal backend PIDs from an identity-verified disposable database, terminate those idle connections using its administrative fixture, require handled error events, then require a different working backend and successful health/readiness. Unit cases test both listeners, log redaction, down/up readiness and health recovery. Local API typecheck and all 363 unit cases passed. API build and release/workbook checks are required before publication; real termination cases and complete exact-source verification must be confirmed in CI and recorded in PR #5. No local PostgreSQL server is installed, so local mocks are not claimed as real restart evidence.

The preceding notification transport/privacy batch is described in NOTIFICATION_GATEWAY_TRANSPORT_REPORT.md. All frozen requirements, acceptance classifications, architecture decisions and production gates remain preserved. This bounded idle-connection recovery does not verify production failover, PITR/RPO/RTO, transaction reconciliation, paging, provider/token lifecycle, full load/accessibility/iOS or signed release acceptance. No merge or deployment.
