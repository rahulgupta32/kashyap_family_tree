# Account-scoped device sessions and governed revocation

Owner: Jyphra Technology Pvt. Ltd. This is bounded implementation evidence for AUTH-FR-007/008/009/011; it does not close final Release 1 acceptance.

GET /auth/sessions requires the current JWT/session/account/MFA guards and returns no-store pages of at most fifty owned, unrevoked, unexpired session records, ordered by creation time and ID. Cursor identity is restricted to the same account. The projection includes only session ID, client-recorded platform/short label, creation/authentication/expiry times and current-session marker. It omits refresh hashes, tokens, device IDs, addresses and user agents. Client labels do not establish trusted hardware identity. Privileged absolute-age/MFA restrictions still determine whether a recorded session can authenticate; this inventory is not a guarantee of effective authority.

POST /auth/sessions/:id/revoke can end another login owned by the caller. Foreign/missing IDs have the same unavailable response; malformed UUIDs fail validation. Ending the caller's own family is rejected in favor of ordinary sign-out. The transaction locks current account/authority/session state and rechecks active, unsuspended, undeleted account, unrevoked/unexpired caller and privileged absolute authentication age. A revoked/suspended caller cannot use previously checked authority to revoke another device.

Migration 053 assigns each existing login its own server-generated family and preserves that family across all refresh successors. Advisory transaction locks serialize rotation and targeted revocation, preventing a stale displayed ID from leaving a refreshed successor active. All members of the selected family retain their existing revocation timestamps; owner_revoked_at distinguishes intentional device sign-out from stolen-token replay. A late refresh from an explicitly ended family returns expired without revoking the user's other logins. Unmarked refresh-token reuse retains the existing universal security revocation policy. The server never accepts a family identifier from a client. Rollback refuses live families or retained owner-revocation markers; rollout requires ordered application/migration staging and an evidence-preserving plan.

The family revocation and redacted LOGOUT intent commit together. Audit write failure rolls back revocation. Lost commit acknowledgement returns fixed 503 and preserves actual committed state; a same-owner retry creates no duplicate intent. Immediate audit delivery failure retains the scheduled retry with a fixed code. Clients treat uncertain responses as unconfirmed, clear old rows and require refresh before retrying. No action issues credentials.

Web navigation and mobile search expose My devices in Nepali/English. Current-device controls are absent, another-device action requires confirmation, lists are paginated, and refresh/error/token/account transitions suppress stale private results. Mobile requests bind to the initiating account through the existing API helper. Labels remain escaped text; response error/provider details are not displayed. No new data is persisted on the client.

Ten real PostgreSQL/HTTP cases cover scoped projection/filtering, pagination/cursor/UUID/current-device rejection, foreign/unknown/revoked/expired/suspended/aged-privileged caller boundaries, concurrent idempotency, refresh successor/simultaneous rotation fencing, explicit-owner late refresh, atomic rollback, lost acknowledgement and scheduled failure recovery. Two real browser scenarios cover confirmed revocation/stale-token denial/current access and unconfirmed/redacted UI state. Three Flutter widget scenarios cover confirmation/current-device controls, uncertain outcomes and late-account responses. The restore rehearsal retains an ended two-record family and independent live session, requiring both owner markers and live status to survive restore.
