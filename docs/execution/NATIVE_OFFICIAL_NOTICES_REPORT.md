# Native official notice destination

Continues the existing `feat/application-completion` implementation without changing the frozen specification, provider contracts, native metadata or release acceptance classifications.

## Demonstrated gap and behavior

The authenticated inbox returns `/broadcasts` for an official announcement. Flutter previously marked such an entry read but had no corresponding destination, so the tap revealed no official notice content. It now opens a read-only official notices screen using the existing server read APIs. Eligible BROADCAST inbox responses include an optional broadcast ID derived from the authorized inbox record. The client accepts it only as a validated UUID locator and requests the exact originating notice detail again, including notices older than the latest 50 summaries. A locator confers no permission: the detail endpoint checks current authority and eligibility. An older inbox response without this field still opens the authorized list destination. An authenticated drawer entry also keeps notices reachable independently of in-app notification preferences. The list contains authorized title/date summaries; selecting one requests its detail again before displaying the body as selectable plain text. There is no native publishing form, arbitrary URL navigation, provider-payload routing or HTML rendering.

`GET /notifications/broadcasts` returns a bare array ordered by creation time and ID descending with a server limit of 50. The client labels a full response as the latest 50 notices and does not invent list pagination. The initial exact-origin detail is fetched independently of whether the originating ID appears in that list. Invalid initial IDs produce a fixed fallback without a network request. `GET /notifications/broadcasts/:id` rechecks verified membership, current audience eligibility and the original recipient snapshot, or current authorized authorship. Existing backend permission, audience, audit and idempotency behavior is unchanged; the optional authenticated locator field does not enter provider payloads.

The screen is bound to its initial API instance and session generation. Authenticated transport already fences requests across replacement sessions while allowing normal token refresh. UI completion checks additionally suppress stale responses. A local 500-millisecond session watch clears already-rendered titles/details after a session change even when no request is pending; it performs no network polling and is cancelled on expiry/disposal. Replacing the API instance clears content immediately and requires reopening the viewer. Updating the originating ID within the same session clears content and invalidates earlier list/detail results. New detail requests and refreshes clear previously displayed bodies before awaiting the server. Missing/restricted, unavailable and malformed responses show fixed bilingual retry or safe fallback messages without raw server diagnostics. Failed detail reads never retain a previous notice body. Summary response bodies and extra fields are ignored, and detail identity must match the selected validated UUID.

This advances the native destination behavior for NOT-FR-007 and existing governed notices under NOT-FR-010. It preserves COM-FR-004 publishing authority by consuming the official broadcast API rather than creating community announcement posts. EC-0167 requires a safe fallback when content becomes unavailable. COM-FR-012 describes community-feed pagination; this bounded official-notice viewer does not claim to complete that separate requirement.
