# Million-Person search repository benchmark

Owner: Jyphra Technology Pvt. Ltd. This report introduces a reproducible fictional benchmark, not final production acceptance.

The guarded script generates a new disposable PostgreSQL database, applies the complete migration stack and inserts exactly 1,000,000 fictional Persons and one recorded name per Person in 25,000-row batches. It never reads a caller-selected application database. Explicit test mode and loopback PostgreSQL are required. Generated database identity is verified before writes; cleanup drops only that generated database. Redacted JSON evidence retains source SHA, migration count, dataset size, database version, fixture duration, workload configuration, latency summaries, correctness failures and cleanup result. No row contents, credentials or real identity data are emitted.

Two scenarios call the actual PersonRepository first-page search: an NFKC-normalized recorded name with a matching private Person that must remain excluded, and a location-only match. Each performs one warmup and twenty measured requests using four closed-loop workers. Correct result IDs/counts are checked on every request. Missing/incorrect observations fail; slow responses remain in the nearest-rank p95 calculation. The job fails if any case exceeds 1,000 ms p95 or has any correctness failure. Three independent metrics regressions verify tail handling, failed/fast responses and missing/invalid evidence.

This measures repository/database search on one generated dataset and one CI runner. It excludes HTTP authentication/projection, devices/network, broad or empty queries, tree rendering, writes, message delivery, representative production distributions, independent arrival-rate load and distributed deployment. Twenty samples are diagnostic evidence, not a robust production percentile estimate. It does not verify 100,000 registered users, 10,000 concurrent connections, full API target-load latency, production infrastructure, resilience or sustained availability. Every such frozen gate remains mandatory. The report sets these production acceptance flags to false.

The first run measures the existing implementation before optimization. No passing latency result is assumed; genuine failures must guide a correction and rerun. Exact commit/run outcomes and retained artifacts are recorded in PR #5 after execution. Local metrics regressions, script syntax and whitespace checks passed before publication. All 260 signed acceptance records and assessment classifications remain unchanged. No merge/deployment.

The function fixes the similarity threshold at the original 0.3 within its own scope, uses caller privileges, and restores the connection setting. Three PostgreSQL regressions compare candidate results directly with the original predicate across Unicode, recorded aliases, fuzzy names, escaped literal wildcards and locations; verify threshold isolation; and check privacy/count/pagination/source preservation. Migration index creation requires planned staging rollout against representative data before any production release.
