# Community reasons and appeals — 2026-10-05

Migration 030 retains new moderation decisions with reason, reviewer and resulting post version. Authors and currently authorized scoped moderators see the latest outcome/reason in the community feed; ordinary readers receive no outcome notes or appeal reasons. Historical decisions cannot be reconstructed and are not backfilled.

An author can appeal a current rejected decision once, providing a 5–1000 character reason and viewed version. The locked post, appeal and durable audit intent commit together. Appeals return to PENDING with a new version and require a currently scoped moderator distinct from both the author and original reviewer. Normal moderation resolves the open appeal; editing or deletion withdraws it. Content edits still require normal independent review. A later rejection is a new decision, not reuse of the old appeal. No role is granted by appealing.

Web and Flutter expose outcome reasons and an appeal action; moderators see the submitted appeal reason in their queue. The web reason entry uses a native prompt; native uses the existing reason editor. Background in-app/push/SMS outcome notification fanout, notification privacy/preferences, dedicated case-history browsing, configurable appeal policy/escalation and richer moderation actions remain mandatory and unimplemented in this checkpoint. This partially advances COM-FR-009 without claiming complete notification delivery or signed acceptance.

Real PostgreSQL HTTP cases cover restricted reasons, author-only appeals, stale/duplicate refusal, original-reviewer exclusion, second-reviewer resolution and audit rollback. Existing workflow suites cover publication/revisions/branch isolation. Exact-head CI is recorded in PR #5; client-specific appeal device/browser scenarios are not claimed.
