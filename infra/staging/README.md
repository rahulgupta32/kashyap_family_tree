# Isolated staging backend

This deployment uses the reviewed API image, PostgreSQL 16, Redis 7, private versioned MinIO storage and ClamAV. Existing API lifecycle hooks run audit, notification, image, cleanup and other workers inside the API process. Run one API replica. The admin is a separate Vercel project.

Provisioning requires owner approval of the exact provider plan, final tax-inclusive price and cost controls. These files create no cloud resources. The previously quoted 4 GB VPS capacity remains unverified until all services, scanner updates and smoke tests run concurrently. Build API images in CI or a build host rather than consuming staging database memory during compilation.

## Secrets and initial configuration

1. Create `/srv/kashyap-staging/{data,secrets,backups}` on the approved staging server disk with owner-only access. The provider's daily disk backup must include these paths. Attached volumes are not included in Hetzner server backups.
2. Copy `environment.example` to the approved secret store and materialize a mode-0600 host `staging.env`. Set reviewed immutable image digests. Build the API using `infra/docker/api.Dockerfile` from the reviewed source commit, publish it to the approved private registry and record that digest. Never use the baseline digest for a later email-login source.
3. Materialize `secrets/api.env` from the approved secret store using `api.env.example` for the existing required names. Preserve production runtime safeguards with `NODE_ENV=production`. Configure `JWT_SECRET`, `MFA_ENCRYPTION_KEY`, independent push-token encryption keys and any configured provider credentials there. No fixed OTP or real member data belongs in this environment. Do not enable fictional admin bootstrap or simulated providers to bypass a failed startup check.
4. Current production SMS setup requires `SPARROW_SMS_TOKEN` and its approved staging sending identity. A separately reviewed restricted staging OTP adapter is required before credentials-free phone evaluation can run. Do not point the production adapter at a fake gateway. Email delivery uses `EMAIL_PROVIDER=brevo`, a domain-verified `EMAIL_SENDER`, `EMAIL_API_KEY` and an independent high-entropy `EMAIL_OTP_HASH_KEY` of at least 32 characters. Store all private values in the approved secret store. `EMAIL_PROVIDER=capture` is limited to isolated development/test processes and cannot establish real delivery acceptance. Real delivery remains pending provider setup.
5. Create a private CA and a server certificate with SAN `DNS:minio`, server-auth usage and bounded lifetime using the approved secret tooling. Materialize the CA certificate as `secrets/minio-ca.crt`, and the server certificate/key as `secrets/minio-tls/public.crt` and `private.key`. Protect the key and retain the CA private key only in the secret store. The MinIO client and API explicitly trust this CA. Renew certificates before expiration. No TLS verification bypass is configured.
6. Store a separate backup decryption identity in the secret store and its public `age` recipient in the backup scheduler. Install `age` on the host. Staging signing keys are generated only within the owner-approved secret workflow and never inside this repository.

Use Docker Engine and Compose supporting `up --wait`, `service_completed_successfully` and image digests. Execute `infra/staging/deploy.sh /absolute/path/staging.env`. Database startup is health-gated. The API awaits its existing advisory-lock-protected migrations before readiness. Storage initialization creates the private bucket, enables versions and grants its dedicated application user access only to that bucket.

## HTTPS and Vercel

The host exposes the API only at `127.0.0.1:3010`. All database, Redis, storage and scanner ports stay on an internal Docker network. API and scanner have outbound connectivity for approved providers and signature updates.

On the authorized Jyphra Tailscale tailnet, enable HTTPS and the host's Funnel permission, then run `tailscale funnel --bg http://127.0.0.1:3010`. Record the resulting `https://<host>.<tailnet>.ts.net` origin. Funnel introduces a provider dependency and bandwidth limits that must be exercised in the real upload/WebSocket smoke tests. Restrict host SSH through the approved management network and firewall; do not expose MinIO or Redis publicly.

Create only `kashyap-staging-admin` in the authorized existing Vercel team, link `rahulgupta32/kashyap_family_tree`, use root `apps/admin`, include source files outside the root, and build the reviewed integration commit. Build the shared workspace packages before `@kashyap/admin`. Configure `NEXT_PUBLIC_API_URL` with the Funnel origin. Set the exact provider admin origin as `STAGING_ADMIN_URL` and redeploy API for CORS. Vercel deployments must remain isolated from existing Jyphra projects. Cross-site cookie behavior and the application's actual admin refresh/MFA journey require live browser acceptance before approval.

## Acceptance and backups

Verify the public `/health/ready` over HTTPS, API migration ledger, authenticated S3 upload/scan/read, Redis, synthetic email/phone login, refresh/logout, admin MFA, genealogy permissions and a WebSocket journey. Preserve the reviewed source SHA, image digests, migration versions, URL origins and timestamped results. Compose readiness alone does not prove those workflows.

Schedule `backup.sh /absolute/path/staging.env /srv/kashyap-staging/backups <age-recipient>` nightly through a restricted root timer. The script pauses the API and its workers, dumps PostgreSQL, stops MinIO to capture consistent object versions, encrypts the database/object pair and restarts services. It retains seven days locally. Enable the provider's seven daily disk backup slots for off-host recovery. Verify scheduler execution and backup completion. This provides daily recovery points and planned backup downtime, not continuous PITR.

Before deployment, take an additional encrypted backup and preserve the previous environment and immutable image digest. An image-only rollback is allowed only after checking that every applied migration is compatible with the previous image. Otherwise stop the API and workers, restore the matching database/object pair into a separate isolated recovery stack, validate it and switch traffic after owner review. Revoke restored sessions and discard old Redis challenges before making recovery accessible. Never automatically run down migrations or overwrite the active database as a rollback shortcut. Test this restore process before marking backups accepted.
